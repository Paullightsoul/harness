# ADR-momentom-07 — Первичные API-контракты

**Дата:** 2026-07-03
**Статус:** начато, не завершено
**Оценка по трекеру:** 4 ч

---

## О чём была задача

Прежде чем разработчик сядет писать код нового backend для админки, ему нужно заранее знать: какие адреса (эндпоинты) будут у нового API, что каждый из них принимает и что возвращает. Без этого фронтенд и бэкенд будут проектироваться вслепую и не сойдутся. В общем списке архитектурных задач это отдельный пункт («Контракт API», приоритет критичный) — нужен черновик формата запросов и ответов (в идеале — OpenAPI) и несколько примеров реальных ответов на настоящих полях прод-базы, а не на выдуманных.

---

## Что решили делать

Не расписывать сразу всё до последнего поля, а сначала обозначить состав по модулям: какие вообще есть разделы API, какие у каждого действия — посмотреть список, посмотреть карточку, изменить, создать. И только для одного раздела — входа в систему — довести контракт до конца, включая точный формат запроса и ответа, потому что именно вход блокирует все остальные разделы (см. ADR-momentom-02 и ADR-momentom-06).

---

## Что сделано по факту

### Список адресов по 10 модулям

По каждому модулю нового API — конкретные адреса, методы и назначение, плюс отметка, требует ли модуль изменений в базе данных:

| Модуль | Фаза | Изменения в БД | Примеры адресов |
|---|---|---|---|
| Авторизация staff | Фундамент | нет | `POST /auth/login/`, `POST /auth/logout/`, `GET /auth/me/` |
| Клиенты | Клиенты и компании | минимальные | `GET /clients/`, `GET /clients/{id}/`, `PATCH /clients/{id}/`, `GET /clients/{id}/companies\|contracts\|documents/` |
| Компании | Клиенты и компании | минимальные | `GET /companies/`, `GET /companies/{id}/`, `PATCH /companies/{id}/`, `GET /companies/{id}/bank-accounts/` |
| Получатели | Получатели | минимальные | `GET/POST /recipients/`, `GET/PATCH /recipients/{id}/`, `GET/POST /recipients/{id}/bank-accounts/` |
| Договоры | Договоры и платежи | нет (без переименования таблицы) | `GET /contracts/`, `GET/PATCH /contracts/{id}/`, `GET /contracts/{id}/payments\|process/` |
| Платежи | Договоры и платежи | минимальные | `GET /payments/`, `GET/PATCH /payments/{id}/`, `POST /payments/{id}/change-status/`, `GET /payments/{id}/timeline\|documents/` |
| Документы | Документы и Telegram | нет | `GET /documents/`, `GET /documents/{id}/`, `POST /documents/upload/` |
| Telegram | Документы и Telegram | нет | `GET /telegram/chats/`, `GET /telegram/chats/{id}/messages/`, `GET /telegram/process/{operation_id}/` |
| Справочники | Справочники и полировка | нет | `GET /directories/countries\|currencies\|partners/` |
| Сотрудники и аудит | Справочники и полировка | минимальные | `GET /staff-users/`, `GET /audit/` |

Итого — порядка 35 конкретных адресов размечено по всем разделам первого этапа, у каждого есть краткое описание, что он делает, и понятно, требует ли он новых полей в базе или отдаёт существующие данные в новом формате.

### Полный контракт для входа в систему

Здесь есть не только список адресов, но и точный формат: что сотрудник отправляет при входе (почта, пароль, код двухфакторной защиты), что получает в ответ (токен, профиль, права), как выглядит выход из системы, как продлевается срок действия входа, как включается и выключается двухфакторная защита. Расписан весь сценарий шаг за шагом — от отправки формы на фронте до записи в журнал на бэкенде. Это единственный раздел, доведённый до состояния «можно кодировать прямо по этому описанию».

### Правило для всех контрактов: без ломающих изменений в базе

Общее правило, зафиксированное сразу для всех 10 модулей: на первом этапе — либо вообще без изменений в базе (данные просто отдаются в новом формате поверх старых таблиц через сериализатор), либо только добавление необязательных колонок. Ни одного модуля с переименованием таблицы или ломающим внешним ключом на первом этапе нет — это тоже часть контракта, просто на уровне данных, а не запроса.

---

## Почему начали именно со входа в систему

Потому что без входа и прав ни один другой раздел не имеет смысла реализовывать — сначала нужно понять, кто и что вообще может делать в системе. Это решение прямо связано с зависимостями, которые описаны в плане работ (ADR-momentom-06): «Блок 1. Каркас» идёт раньше «Блока 2. Клиенты и компании» именно поэтому.

---

## Что дальше

- Довести до полного формата контракты по остальным 9 модулям — по образцу того, как уже сделано для входа в систему, начиная с клиентов и компаний (следующие по плану).
- Свести всё в единый файл-схему API (OpenAPI), чтобы фронтенд и бэкенд разработчики могли сверяться с одним источником правды, а не с разрозненными списками.
- Подготовить 2–3 примера реальных ответов API на настоящих данных прод-базы (клиент, договор, платёж) — как ориентир для фронтенда, ещё не сделано.
