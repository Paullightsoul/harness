# Systematic Debugging — 4-фазный root-cause

Когда гейты красные или ревьюер вернул CHANGES — не патчь вслепую.
Пройди 4 фазы методично.

## Когда активировать

- Гейты проекта красные после первой попытки воркера.
- Ревьюер вернул CHANGES с конкретными проблемами.
- Оркестратор делает re-plan после исчерпания попыток.
- Эскалация на сильную модель (kimi/glm) — перед новым заходом.

## 4 фазы

### Фаза 1: Root-Cause Tracing

**Цель**: найти корень проблемы, а не симптом.

```
1. Прочитай ПОЛНЫЙ вывод упавшего гейта (не только последние строки).
2. Найди ПЕРВУЮ ошибку — часто каскад начинается с неё.
3. Открой файл и строку, указанные в трейсбеке.
4. Проследи цепочку вызовов: откуда пришли плохие данные?
5. Сформулируй гипотезу: «корень в X, потому что Y».
```

**Не делай**: «наверное, здесь нужен try/except» → это маскировка, не фикс.

### Фаза 2: Defense-in-Depth

**Цель**: фикс, который не сломает остальное.

```
1. Минимальное изменение, закрывающее root cause.
2. Проверь: не сломал ли фикс смежную логику?
3. Если фикс затрагивает интерфейс — проверь все места вызова.
4. Добавь тест, воспроизводящий баг (регрессия).
```

### Фаза 3: Condition-Based Waiting

**Цель**: убедиться, что фикс стабилен.

```
1. Прогони ВСЕ гейты проекта (не только упавший).
2. Проверь edge cases, упомянутые ревьюером.
3. Если тесты flaky — стабилизируй (не удаляй).
```

### Фаза 4: Verification

**Цель**: подтверждение.

```
1. Прогони полный набор гейтов.
2. Сравни diff с тем, что было в предыдущей попытке.
3. Убедись, что новые изменения — только фикс, без побочных правок.
```

## Матрица типичных провалов

| Симптом | Типичный root cause | Фаза 1 действие |
|---------|--------------------|--------------------|
| `ImportError` | Несуществующий модуль/функция | Проверь реальный API файла |
| `TypeError: missing arg` | Изменился интерфейс | Прочитай сигнатуру, не угадывай |
| `AssertionError` в тесте | Логика не соответствует спеке | Перечитай acceptance criteria |
| `mypy: incompatible type` | Неверный тип в сигнатуре | Прочитай type-аннотации зависимости |
| `lint: unused import` | Остатки от предыдущей попытки | Удали, не комментируй |

## Для re-plan (оркестратор)

Когда оркестратор видит фидбэк от провалившихся попыток:

1. **Повторяющиеся ошибки** → задача размытая → `refine` спеку, уточнив
   конкретные интерфейсы и типы.
2. **Разные ошибки каждый раз** → задача слишком большая → `split` на
   более узкие подзадачи.
3. **Ошибки доступа/данных** → не хватает контекста → `block` с описанием
   чего не хватает.

## Связь с harness

- Применяется на шагах RUNNING (повторные попытки) и ESCALATE (re-plan).
- Фидбэк ревьюера (`=== ФИДБЭК РЕВЬЮЕРА ===`) — входные данные для Фазы 1.
- Гейты проекта — объективная проверка для Фаз 3-4.
- Лестница эскалации (auto → kimi → glm) даёт более сильную модель для
  сложного root-cause анализа.
